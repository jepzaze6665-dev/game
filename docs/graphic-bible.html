BANNERFALL: FOUR REALMS
GRAPHIC BIBLE

The art, animation and UI standard for the game. Every sprite, palette, icon and UI element on this page is rendered live from the game code, so what you see here is exactly what ships. When the code changes, this page changes with it.

STATUS

1 · CORE VISUAL IDENTITY

Original 2D pixel-art browser strategy game. Large groups of small, readable units fight side-versus-side on a wide field. Compact colourful characters, clear silhouettes, simple but expressive animation and a strong arcade battle HUD. The look is inspired by the general principles of classic browser lane-battle games (density, scale, composition, HUD placement) — never by any specific game's art. All characters, buildings, icons, effects and UI are original and generated by our own procedural rig.

STYLE

  • Chunky pixel art, integer-scaled, nearest-neighbour — never blurred
  • Colourful cartoon fantasy / sci-fi
  • Slightly exaggerated proportions, oversized heads and weapons
  • One-pixel dark outline () on every sprite
  • Simple shapes, controlled detail, subtle two-step shading
  • Bright but controlled colours; team read first, race second

THE GAME SHOULD FEEL

  • Energetic
  • Strategic
  • Readable at a glance
  • Nostalgic
  • Polished and lightweight

AVOID

  • Photorealism or military-sim realism
  • 3D models, cinematic lighting
  • Excessive particles that hide the fight
  • Muddy or dark palettes
  • Tiny unreadable detail
  • Modern mobile / SaaS UI clutter
  • Imitating existing games' assets

2 · CAMERA AND BATTLEFIELD

Fixed orthographic camera, slight top-down tilt implied by the sprites (feet lower than heads, shadows below). No rotation, no zoom, no orbit: the field is always visually stable. Units move horizontally.

GROUND THEMES

A dirt lane on a grass field. Each campaign theme recolours the same field generator: four grass tones, three dirt tones, stone, flowers, trees, optional water. The battlefield stays clean — decoration lives outside the lane.

Density targets: 10–30 units comfortable · 30–60 busy but readable · 60+ still organised (see §18 for the live crowd test). The engine supports 220 units per team.

3 · UNIT SCALE source cells, world scale and the ground anchor

Sprites are authored at native pixel resolution in small cells and drawn at 12 pixels per world unit, then the whole frame is scaled by an integer (×1 to ×3 depending on window size). A humanoid is 30×32 source pixels: ~60–96 screen pixels tall on a desktop display. Every body type has its own cell.

Ground anchor rule. Every cell has a fixed anchor (cx, fy): the feet sit on row fy, horizontally centred on cx. The renderer places the anchor on the unit's world position and draws the shadow at the same point. Nothing floats, nothing sinks — a unit that violates the anchor is a bug, not a style choice.

4 · CHARACTER PROPORTIONS

Stylised, not realistic: an oversized head, compact torso, readable limbs, large recognisable weapon. The humanoid drawer has three size presets shared by the whole roster, so proportions never drift between artists or races.

At small size the player must identify, without zooming: 1. race (palette + headgear), 2. class (weapon + body), 3. threat level (body size + gold trim), 4. weapon type (silhouette).

5 · SILHOUETTE RULE

Every unit must have a unique silhouette. Below, one race's 12 units are filled solid: if two shapes read the same, one of them needs a different weapon, headgear or body.

CLASS SILHOUETTES

  • Sword — blade clearly visible, compact armoured body
  • Spear / halberd — long diagonal line extends the silhouette
  • Archer — bow arc, lighter body, quiver
  • Heavy / tank — big body preset, shield or plate mass
  • Mage / priest — staff with gem, robe hides legs
  • Assassin — narrow body, dual curved weapons
  • Machine — mech, vehicle or robot body; metal legs
  • Undead — bandage wrap, skull, jackal mask, unusual posture

NEVER

  • Two units that differ only by colour
  • A weapon hidden behind the body in the idle pose
  • A higher tier that is "the same unit, bigger numbers"

6 · FOUR RACES identity, palette, emblem, base and full roster

Race colours live in src/data/races.js (UI) and each roster file's palette constant (sprites). Team colour (blue player / red enemy) is a separate token layer: any palette entry marked T becomes the team colour at build time, so every race exists in both a blue and a red version.

7 · CHARACTER TIERS

Each race has 12 units in the same twelve roles, unlocked left to right on the deployment bar. Cost rises with tier; the value normaliser (src/data/balance.js) keeps value-per-gold on one curve for all races. Visually, higher tiers must bring a new silhouette, new equipment, new effects and a stronger identity — not a scaled-up copy.

8 · SPRITE SHEET STANDARD

Frames are generated by the rig (src/art/rig.js) and packed into one 2048² atlas at load time. The per-unit set is deliberately small so 400+ units animate cheaply:

SETFRAMESNOTES
Idle1Also used as the HUD icon
Walk4stride / bob cycle, arm swing
Attack3anticipation → impact → recovery, chosen per weapon (§9)
Hurt1lean back, weapon down, eyes closed; plus a white flash and jitter in the renderer
Death0renderer rotates the idle frame 90° over 0.3 s and fades it out — no gore, no extra frames
Downed / revive0rotated frame pulsing in alpha until the unit rises (undead)

Both team versions of every frame are prebuilt (blue and red). Transparent background only; no scenery inside a sprite.

9 · ANIMATION STYLE

Fast, readable, slightly exaggerated, arcade-like. Three-frame attacks with a clear anticipation pose, a strong impact pose (with the slash / cast flag that triggers the effect) and a short recovery. The attack set is chosen by weapon, so a new unit gets correct motion for free:

IDLEsingle frame; life comes from the renderer (spawn hop, flyer hover, cheer bounce)WALK4-frame cycle: legs alternate lift, body bobs one pixel, arm swings 65°–100°; heavy bodies kick up dustHIThurt frame + white flash + 0.12-unit jitter for the hit-stun durationDEATHtopple away from the killer, fade; big units also shake the camera

10 · UNIT SHADOWS

Every unit has a soft elliptical shadow directly under its feet. Shadows are team-tinted (blue / red) — the single most important friend-or-foe read in a scrum, because it stays visible under overlapping sprites.

DEPLOYMENT CARDS

Each card: hotkey (top-left), squad size (top-right), icon, name, cost. States: affordable (gold inner border, gold cost), poor (desaturated, red cost), cooldown (dark fill rising from the bottom with seconds), locked (grey, padlock), recommended (pulsing glow, COUNTER! ribbon).

13 · UI STYLE tokens from css/style.css

Dark semi-transparent panels, bevelled 3-px borders with an inner dark line, chamfered corners (clip-path), a hard drop shadow instead of blur. Two fonts only: Press Start 2P for headings, numbers and labels; Pixelify Sans for body copy. No glassmorphism, no soft gradients, no rounded SaaS buttons, no neon.

14 · ICON DESIGN

A unit's icon is its idle frame, drawn at an integer scale that fits a 44-px box (32 px on phones). The icon can never drift from the battlefield sprite because it is the same pixels. Icons are always the player (blue) version.

15 · BASE DESIGN

Four original bases in a 76×84 cell with four damage states (intact → rubble). A base is recognisable but must not dominate the lane; it sits at the far left / right with its banner in team colour.

16 · COLOR SYSTEM

LAYER 1 · TEAM

Cloth, banners, gems and shadows marked T/t/L take the team colour. Team must read before anything else.

LAYER 2 · RACE

Skin, armour, trim and accent are race constants (§6). Human steel & gold, Demon crimson & orange, Robot cyan & grey, Mummy sand & turquoise.

LAYER 3 · SHARED MATERIALS

Metal, wood, gold, bone and outline are global constants so weapons look consistent across races.

Never rely on colour alone to say what a unit is. Silhouette + equipment + colour work together; colour-blind players still get team from shadow brightness and race from shape.

17 · READABILITY TEST

Every unit passes three checks. Pick a unit to see it at the three integer screen scales the renderer actually uses, then in a 25-unit scrum.

Test 1: recognisable at ×3 · Test 2: at ×1 · Test 3: class still readable in the crowd

18 · CROWD BATTLE TEST live

Four scenes drawn with the real frames, shadows and draw order (sorted by lane depth). Check overlap, faction distinction, shadow read and projectile visibility. Click a scene to reshuffle.

19 · TECHNICAL ART REQUIREMENTS

The renderer draws the whole world into a low-resolution canvas (window ÷ integer scale) and lets CSS stretch it with image-rendering: pixelated. One instanced quad batch draws every sprite from the single atlas texture with nearest filtering; there is exactly one draw call for all units, effects and bases.

20 · ASSET STRUCTURE

There are no image files. Every asset is code, which is why this bible can render itself. If a hand-painted asset is ever introduced it must be packed into the same atlas at the same cell sizes and anchors.

21 · CHARACTER DESIGN WORKFLOW

  1. Read this bible; check the race's palette and existing silhouettes (§5, §6).
  2. Design the unit as a look: body preset, palette, headgear, weapon, extras. Prefer an existing part; add a new part to rigParts.js only when the silhouette needs it.
  3. Check it in the atlas viewer (tools/atlas.html?s=6&f=<id>): anchor, outline, both team versions, all frames.
  4. Run the readability test (§17) and the crowd test (§18) on this page.
  5. Lock the style: compare against the other 11 units of the race in the roster screen.
  6. Test in a real battle (?bg=1, GAME.startBattle, GAME.autoplay).
  7. Run npm test and the balance matrix if stats changed.
Never design all 48 units independently. New parts must be shared by at least the race's other units where sensible; a one-off detail that nobody else uses is usually noise.

22 · CONCEPT ART & AI-GENERATION RULES

When concept art (hand-drawn or AI-generated) is used to explore a unit before it is built in the rig, it must follow these priorities and constraints. Concept art is reference for the rig, never a shipped asset.

PRIORITISE

  1. Silhouette
  2. Readability
  3. Consistent proportions (§4)
  4. Faction identity (§6)
  5. Weapon readability
  6. Animation compatibility (§9)
  7. Visual hierarchy by tier (§7)

DO NOT

  • Excessive detail, cinematic backgrounds
  • Photorealistic rendering
  • Cropping, text, logos, UI or scenery in the image
  • Copying any existing game's character, costume, weapon or artwork

OUTPUT

  • Full body, feet visible, complete weapon
  • Front / three-quarter game view, facing right
  • Centred on a plain or transparent background
  • Flat colour blocks with two-step shading

24 · FINAL QUALITY STANDARD

The finished game looks like a polished, original classic browser strategy battle with hundreds of small visual decisions serving play. At any moment the player must instantly see: who they are (blue, left), who the enemy is (red, right), where units are moving, which are fighting, which card is selected, how much gold they have, and how much base health remains.
